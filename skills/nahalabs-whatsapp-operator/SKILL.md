# NahaLabs WhatsApp Operator — the one skill for WhatsApp on every app

**One Operator. Deployed once. Every app you build points at the same URL.**
Business owner scans a QR code to activate their own number. They then share that number
(or a `wa.me` link) with their customers. No Meta approval, no per-message bill, free until
you have a paying customer.

Full reference contract (schema, HMAC scheme, code): `references/whatsapp-operator-contract.md`.
Live implementation: `operator/` at the repo root, deployed via `render.yaml`.

---

## 1. The two-server split — never violate this

| Component | Where it runs | Owns |
|---|---|---|
| **Core (Brain)** | Your app, on Vercel (serverless) | UI, auth, DB, business logic, AI, outbox, `/api/webhooks/whatsapp` |
| **Operator (Engine)** | `operator/` on Render (Docker, always-on) | 24/7 Baileys socket, QR pairing, send/receive, delivery state |

The socket must never live inside a serverless function — it dies the moment the function goes cold.

---

## 2. One Operator, unlimited apps

Deploy the Operator **once**. Every app you build gets the same `OPERATOR_URL` +
`OPERATOR_API_KEY`, and creates its own `wa_account_id` (one per business) bound to its own
`appId` + `tenantId` + `webhookUrl` via `wa_account_bindings`. The Operator resolves each inbound
message to the right app and fans it out — see `POST /accounts` in §5.

```
Flavourly (app_id="flavourly")  ──┐
CargoIQ   (app_id="cargoiq")    ──┼──►  ONE Operator  ──►  wa_account_bindings routes each
Your next app (app_id="...")    ──┘        (Render)         message to the right webhook_url
```

## 3. The two QR codes — do not confuse them

1. **Pairing QR (link-a-device)** — ephemeral, TTL-bounded (`PAIRING_QR_TTL_SECONDS`, default
   120s), lives **only in memory on the Operator, never in Postgres**. Generated by
   `POST /accounts/:id/pair`, fetched via `GET /accounts/:id/qr`. The **business owner** scans
   this **once**, in their dashboard, to link their phone number.
2. **Customer chat QR / `wa.me` link** — stable, built client-side from the connected
   `phoneNumber` (`https://wa.me/<number>?text=Hi`). Shown permanently in the owner's dashboard.
   The owner downloads/shares **this** with their customers — a completely different artifact
   from the pairing QR, and it never expires.

## 4. The owner activation flow (build this in every Core app's dashboard)

```
Owner clicks "Connect WhatsApp"
        │
        ▼
Core: POST {OPERATOR_URL}/accounts
      { appId, tenantId, webhookUrl }              ← creates wa_account_id + binding
        │
        ▼
Core: POST {OPERATOR_URL}/accounts/:id/pair         ← starts the Baileys socket
        │
        ▼
Core dashboard polls GET {OPERATOR_URL}/accounts/:id/qr  every ~2s
        │  renders `qr` as a QR code (e.g. the `qrcode.react` package)
        ▼
Owner scans with WhatsApp → Linked Devices (once)
        │
        ▼
Core polls GET {OPERATOR_URL}/accounts/:id/status until isConnected: true
        │
        ▼
Dashboard now shows the STABLE customer QR / wa.me link (built from `phoneNumber`)
        │
        ▼
Owner downloads it / puts it on a table tent, receipt, Instagram bio, etc.
```

Owner's phone can be switched off after pairing — the Operator holds the session 24/7.

## 5. Operator API surface

All routes except `/health` and `/ready` require `Authorization: Bearer <OPERATOR_API_KEY>`.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/health` | liveness — point your keep-alive scheduler here |
| `GET` | `/ready` | readiness — confirms Postgres is reachable |
| `POST` | `/accounts` | **create** a `wa_account_id` + binding: `{ label?, appId, tenantId, webhookUrl }` → `{ waAccountId }` |
| `GET` | `/accounts?appId=&tenantId=` | list every number a tenant has connected |
| `POST` | `/accounts/:id/pair` | start the socket, begin generating a pairing QR |
| `GET` | `/accounts/:id/qr` | current ephemeral pairing QR (`410` once expired — call `/pair` again) |
| `GET` | `/accounts/:id/status` | `{ isConnected, phoneNumber }` |
| `POST` | `/accounts/:id/disconnect` | graceful logout — owner must re-scan to reconnect |
| `POST` | `/send` | `{ waAccountId, to, text }` — reply to a customer |

> **Note:** `POST /accounts` and `GET /accounts` are the pieces most starter versions of this
> Operator miss — without them there is no `wa_account_id` to pair in the first place. If your
> deployed `operator/src/store.js` / `server.js` don't have `createAccountWithBinding` /
> `listAccountsForTenant` and the corresponding routes yet, apply the patch in
> `references/account-creation-patch.md` before wiring up a new app.

## 6. Message flows

**Inbound (customer → your app):**
```
Operator receives → persists → resolves wa_account_bindings → claims an idempotent
inbound_delivery per binding → signs payload (HMAC v2) → POST webhook_url → 200 fast
```

**Outbound (your app → customer):**
```
Your app's outbox dispatcher → POST {OPERATOR_URL}/send (Bearer key) → Baileys sends
```

Core-side webhook reference: `operator/reference-core-webhook.route.ts` —
verify HMAC → validate with Zod → persist → enqueue a durable job → return `{ ok: true }` fast.
**Never** run AI/business logic inside the webhook request itself.

---

## 7. HMAC v2 (both directions)

```
signature = hex( HMAC-SHA256( secret, `${timestamp}.${nonce}.${rawBody}` ) )
Headers: X-Signature, X-Timestamp, X-Nonce
Verify with crypto.timingSafeEqual + a timestamp tolerance (default 300s) to block replay.
```
`WEBHOOK_SECRET` signs Operator→Core webhooks. `OPERATOR_API_KEY` (Bearer) authenticates
Core→Operator calls. Both must match exactly between the Operator and every Core app.

---

## 8. Session persistence (why reconnects don't require a re-scan)

`wa_sessions` stores **both** `creds` and `keys` (Baileys `BufferJSON`-serialized), keyed by
`wa_account_id`. If your fork only persists `creds`, sessions will silently break after a
restart — always persist both.

---

## 9. Safety, control & compliance

- **Global kill switch:** a database-backed toggle your Core app checks before letting AI reply —
  never an env var (needs to flip instantly, without a redeploy).
- **Per-tenant manual mode:** log inbound messages but suppress AI replies for that tenant.
- **POPIA/GDPR:** detect `STOP` / `UNSUBSCRIBE` / `OPT-OUT` in inbound text and blocklist that
  sender for that tenant immediately; never message a blocklisted number again.
- **INV-1:** exactly one live socket per `wa_account_id`, regardless of how many apps bind to it.
  A cross-account message leak is Sev-1.

## 10. Deploying the Operator (once)

See `docs/WHATSAPP_RENDER_DEPLOY.md` for the full walkthrough. Summary:

1. `openssl rand -hex 32` twice → `WEBHOOK_SECRET`, `OPERATOR_API_KEY`.
2. Get a Postgres connection string (Neon free tier is fine).
3. Render → **New → Blueprint** → connect the repo → Render reads `render.yaml` → enter the
   three secrets (`DATABASE_URL`, `WEBHOOK_SECRET`, `OPERATOR_API_KEY`) → **Apply**.
4. Confirm `GET /health` and `GET /ready` both return 200.
5. Add a **cron-job.org** job hitting `/health` every ≤10 minutes (Render free tier sleeps —
   never rely on a browser timer or a Vercel cron for this).
6. Copy the service URL into every Core app's `OPERATOR_URL`, `OPERATOR_API_KEY`, `WEBHOOK_SECRET`.

## 11. Guardrails for the coding agent

- Never import Baileys into a Core app — only the Operator touches `@whiskeysockets/baileys`.
- Never store a pairing QR in Postgres — memory + TTL only.
- Never run the socket in a serverless function.
- Never introduce Twilio, Evolution API, 360dialog, or the paid Cloud API without the user
  explicitly asking for it.
- Never let `POST /send` bypass the Core app's outbox/idempotency layer — the Operator sends
  exactly what it's told; duplicate-prevention is the Core app's job.
- Before wiring a new app to this Operator: confirm `POST /accounts` exists (§5); if not, apply
  the patch first.
